# Mastodon 仕様

ビルドや開発の進め方ではなく、サーバーが外部（Mastodon など）に対して
何をどう応答するかをまとめる。ビルドは [README.md](../README.md)、
横断的な設計は [architecture.md](architecture.md) を参照。

ここで出てくる `DOMAIN` の指定は
[README.md](../README.md) の「環境変数」を参照。

## 仕様の決め方

振る舞いは基本的に Mastodon に合わせる。
ActivityPub で決まっていないところや、実装ごとに違うところは Mastodon の振る舞いを正とする。
合わせないときは、その理由をコードコメントとこの文書に書く。

## エンドポイント

| パス | 内容 |
| --- | --- |
| `GET /.well-known/webfinger?resource=acct:<name>@<domain>` | アカウント発見の 1 ホップ目 (RFC 7033) |
| `GET /users/{name}` | Actor JSON。プロフィールと公開鍵 |
| `POST /users/{name}/inbox` | アクティビティの受け口。HTTP Signatures を検証する |
| `POST /inbox` | 共有 inbox。全アカウントで 1 つの受け口で、検証と処理は `/users/{name}/inbox` と同じ |
| `GET /users/{name}/followers` | フォロワーの OrderedCollection。`?cursor=` で中身 |
| `GET /users/{name}/outbox` | 配信した `Create` の OrderedCollection。`?cursor=` で中身 |
| `GET /users/{name}/collections/featured` | プロフィールに載せる投稿の OrderedCollection |
| `GET /notes/{id}` | 配信した投稿。相手がパーマリンクとして引きに来る |
| `GET /.well-known/nodeinfo` | NodeInfo の discovery document |
| `GET /nodeinfo/2.1` | サーバーの実装と規模。調査用 |

`{name}` として応答するのは、管理画面から登録したユーザー。
詳しくは下の「アカウントの引き当て」を参照。

サーバーが持つパス以外は静的ファイルの配信に落ちる。どの画面が出るかは
[README.md](../README.md) の「画面のパス」を参照。

アクターと投稿の `url`（人が開くページ）はまだ出さない。アカウントと投稿を表示する画面が
無いため。出さなければ相手は `id` に倒すので、開けないページを指すより JSON のパスが開く方がまだ読める。
画面を作ったら `:backend` から `WebPageUrls` を渡す。

投稿の `id` にアカウントの名前を入れないのは、名前が変わっても相手が覚えている
値が指す先を変えないため。

Actor は `endpoints.sharedInbox` に `/inbox` を出す。相手は同じサーバー宛ての配信を
ここへ 1 通にまとめる。出さないと、共有 inbox にしか配らない実装から届かない。

共有 inbox には宛先のアカウントが無いので、`Follow` と `Undo{Follow}` は `object` の
アクターから宛先を引く。`object` が id だけの `Undo` は、記録している `Follow` の id から
どのアカウントへのフォローかを引く。

inbox は署名が通れば 202、通らなければ 401 を返す。検証の内容は
[HttpSignatureVerifier.kt](https://github.com/matsudamper/kotpub/blob/main/activitypub/src/main/kotlin/net/matsudamper/activitypub/httpsignature/HttpSignatureVerifier.kt)
の KDoc にある。

届いたアクティビティのうち処理するのは `Follow` と `Like` と `EmojiReact` と `Undo` と
`Update` と `Delete` の 6 つ。`Follow` はフォロワーとして記録してから相手の inbox に `Accept` を返す。
`Like` はこちらが配信した投稿へのお気に入りかスタンプとして、`EmojiReact` はスタンプとして
記録する。`Undo` は `object` が何だったのかで、フォローの記録かお気に入りかスタンプの
どれかを消す。`Update` は送り主自身の
アクターが `object` に埋め込まれて
いるときだけ、記録している表示名・`preferredUsername`・プロフィールの URL・アイコンの
URL を置き換える。inbox と公開鍵は触らない。`Delete` は送り主自身の削除のときだけ、
その相手のフォローとお気に入りとスタンプを全部消す。それ以外の種類は種類と送り主をログに出すだけ。

Mastodon のお気に入りは `content` を持たない `Like` で届く。Misskey は押した絵文字を
`content` に載せた `Like` を、Pleroma は同じ形の `EmojiReact` を送ってくる。
Mastodon は絵文字付きの `Like` もお気に入りとして数え、`EmojiReact` は受け取らないが、
ここではどちらもスタンプとして記録する。お気に入りとして数えると、押された絵文字を
公開画面に出せない。カスタム絵文字は `content` に `:name:` としか入らないので、画像は
同じアクティビティの `tag` にある `Emoji` から取る。

お気に入りは Mastodon と同じく、投稿と押した相手の組で 1 つとして記録する。受け取った
`Like` アクティビティ自身の `id` は持たないので、取り消しの `Undo` は `object` に `Like` が
丸ごと埋まっているときだけ、その `Like` の `object`（対象の投稿）で引き当てられる。
`object` に `Like` の `id` だけが入った `Undo` は、Mastodon と同じくお気に入りの取り消し
としては扱わない。`Undo` が対象の `Like` より先に届いたときは、押した相手と `Like` の
`id` を 6 時間覚えておき、後から届いたその `Like` を記録しない。これも Mastodon と同じ。

スタンプは Misskey と同じく、投稿と押した相手の組で 1 つとして記録し、押し替えたら
置き換える。取り消しと、先に届いた取り消しの扱いはお気に入りと同じで、`EmojiReact` にも
当てはめる。取り消しは投稿と押した相手に加えて絵文字でも引き当てる。押し替えた後に
古いスタンプの取り消しが届いたときに、今のスタンプを消さないため。

記録は DB に残るので、再起動してもフォロワーは残る。`Accept` を返せなかった
フォローは記録には残るがフォロワーには数えない。相手から見て成立していないため。

アカウントを削除した相手からの `Delete` は、そのとき既に相手のアクター文書が無く、
公開鍵を取りに行けない。フォローとお気に入りとスタンプのどれを受けたときも、相手の
アクターを公開鍵ごと記録してある（公開鍵は相手 1 人につき 1 つ）。記録のある相手なら
それで検証して、フォローとお気に入りとスタンプを消す。お気に入りやスタンプだけを押した
相手を記録しないと、消えた相手のお気に入りやスタンプが公開画面に出たままになる。記録した鍵を
使うのは、相手のサーバーが 410 を返したときだけ。取りに行けなかっただけの場合にも
使うと、相手が鍵を替えた後に古い鍵で署名が通る。404 は消したのか置き場所が変わった
のかを区別できないので、取りに行けなかった側に入れる。

記録した鍵は、相手の文書を読めたときに読み直したもので置き換える。`Follow` のときの
鍵のままにすると、相手が鍵を替えてから消えた場合に検証できない。

フォローもお気に入りもスタンプも残っていない相手の鍵は引かない。関わりの切れた相手の鍵を返すと、
その鍵を持っている者が本人の `Delete` を装える。

記録の無い相手からの `Delete` は検証できない。この 1 つだけは検証できなくても 202 を
返す。401 を返すと相手が同じものを送り直し続けるため。検証していないので中身は信用せず、
受け流すだけで何もしない。フォロワーではないので消すものも無い。

コレクションは 2 段構え。パラメータが無ければ総数と最初のページへの入口だけを返し、
`?cursor=` を付けるとページの中身を返す。空の `?cursor=` が先頭のページで、続きは
応答の `next` に入っている URL をそのまま辿る。何件目かで指さないのは、読んでいる間に
増減があると同じものが 2 回出たり抜けたりするため。

## 投稿を配る

`Note` を `Create` に包んで、フォロワーの inbox に署名付きで POST する。
`sharedInbox` を持つ相手はそちらにまとめるので、同じインスタンスに何人いても 1 通で済む。

送る前に投稿を記録する。相手は受け取った直後に `object.id` をパーマリンクとして
引きに来ることがあり、配信が先だとそこで 404 を返してしまう。

配信はその場では行わず、宛先ごとに配信キュー（`delivery_queue`）へ投函してワーカーが送る。
届かなかった宛先は 30 秒から 2 倍ずつ間隔を伸ばして送り直し（24 時間で頭打ち）、
投函から 30 日を過ぎたら諦める。送信中にプロセスが落ちた行は次の起動で送り直すので、
同じ `Create` が 2 回届くことがある。受信側はアクティビティの `id` で重複を判定する前提。
`Accept{Follow}` と `Delete`、`Update{Actor}` はキューに載せず、今まで通りその場で送る。

`Follow` が初めて成立したら、その相手の inbox にだけ、成立より前の直近 20 件の投稿を
`Create{Note}` として配り直す。送るのは inbox の応答を返した後で、
`Follow` の送り直しでは配らない。`Create.id` と `Note.id` と `published` は
初回配信と同じものを保存済みの投稿から組み立てるので、相手が既に持っている
投稿は重複として落ちる。`sharedInbox` は使わない。まとめて送ると、同じサーバーの
他のフォロワーにも同じ投稿が届く。

Mastodon は未フォローのプロフィールを開いたとき `outbox` ではなく Actor の
`featured` を引きに来る。`featured` エンドポイントは将来の
ピン留め用に用意しているが、いまは空のコレクションを返す。
投稿数の表示だけ出て中身が空なのは、`outbox` の `totalItems` を読んでいるためで、
タイムライン欄とは別の話になる。

`outbox` は ActivityPub のアクター情報として配信した `Create` を返すが、
Mastodon も Misskey もフォロー成立時にこれを遡って過去投稿を取り込まない。
未フォローの投稿一覧は `featured`、フォロー成立後の過去投稿は
こちらからの `Create` の再配信で補う。

発火させるのはログインしたユーザーの投稿カラムで、GraphQL の `user.postNote` を叩く。
本文はプレーンテキストで受けて段落と改行だけの HTML に組み立てる。
HTML をそのまま受けると、画面を通して任意のタグをフォロワーに配ることになる。

投稿の削除はまだ画面から行えない。消すときは `object` を `Tombstone`（墓標。消えたオブジェクトを表す ActivityStreams 2.0 の型）にした
`Delete` を、元の投稿と同じ `to` と `cc` で配る。
こちらの記録を消してから配る。配信が先だと、受け取った相手が確かめに来たときに
まだ本文を返してしまう。届かなかった相手のタイムラインには投稿が残る。

## アカウントの削除

まだ画面からは行えない（repository の `AccountRepository.markDeleted` まで）。消すときは `object` に自分のアクター id を入れた
`Delete` を、消える直前のフォロワーの inbox に配る。`object` が送り主自身でないと、
相手はアカウントではなく投稿の削除として扱う。

`Delete` 自身の id は削除のたびに変える。アクターの id から決めた固定の値にすると、
同じ名前で作り直して再度消したときに、相手の重複判定で 2 回目が落ちる。

配らないと相手側にアクターとフォローの関係が残り、同じ名前で作り直したときに
フォローしていない相手に投稿が届いたように見える。届かなかった相手には残る。

こちらの記録はアカウントの行から先に消す。消えるとその名前は引き当てられなくなり、
配信の途中に `Follow` を受けたり投稿したりできなくなる。名前で持っている投稿と
フォロワーとログイン中のセッションはその後に消す。

```sh
curl "http://localhost:8080/.well-known/webfinger?resource=acct:admin@example.com"
curl -H 'Accept: application/activity+json' http://localhost:8080/users/admin
```

外から見えるようにするには HTTPS が要る。開発中は Cloudflare Tunnel や ngrok で
`DOMAIN` に指定したホスト名に向ける。

## プロフィールの表示名と説明文

Actor の `name` と `summary`。保存先は `accounts.display_name` と `accounts.summary`。
編集する画面はまだ無い。未設定なら `name` はユーザー名、`summary` は空になる。

`summary` は HTML として解釈されるので、保存はプレーンテキストで持ち、配信するときに
空行で段落、行の切れ目を `<br>` にした HTML へ組み立てる。

プロフィール画像・ヘッダー・リンク集（`icon`・`image`・`attachment`）は出さない。

## アカウントの引き当て

WebFinger の `resource` とパスの `{username}` は同じ経路で引き当てる
（`ActorDirectory.kt`）。片方だけで引けると「検索には出るが開けない」という
分かりにくい壊れ方になる。

引き当たるのは `accounts` テーブルにある名前（管理画面から登録したユーザー）で、無ければ 404。

大文字小文字は区別しない。返すのは保存されている綴りで、要求された綴りではない。
`User1` と `user1` を別のアクター ID として返すと、相手側に両方がキャッシュされる。

鍵はまだアカウントごとに持っていない。どのアカウントも同じ秘密鍵で署名する。

検証に使ったアカウントは、名前を変えて作り直す。Mastodon はリモートのアカウントを
永続キャッシュするので、一度間違った内容を取得されると相手側からは直せない。

## アクターの鍵

鍵は消さずに持ち続ける必要がある。読み込み元は 2 つあり、同時には指定できない。
両方が設定されていると起動時に落とす。

| 指定 | 動き |
| --- | --- |
| `ACTOR_PRIVATE_KEY_PATH`（既定） | ファイルがあれば読む。無ければ生成して書き出す（所有者のみ読み書き可） |
| `ACTOR_PRIVATE_KEY_PEM` | PEM をそのまま使う。ファイルには書き出さない |

どちらから読んだかは起動ログに出る。生成した場合だけ警告になるので、
運用中に出ていたら以前の鍵を失っていることになる。

保存するのは秘密鍵だけで、公開鍵は起動のたびに秘密鍵から導く。
鍵を持ち続ける理由とこの判断の理由は `ServerEnv.kt` の KDoc にある。
